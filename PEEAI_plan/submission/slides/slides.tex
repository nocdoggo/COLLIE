\begin{frame}{An agent that acts on a text can spend money on a rumor, so Plan B checks first}

    \includegraphics[width=\textwidth]{fig_contrast.pdf}

  \support{In Plan B the model never acts on its own. It picks one option the server checked, and \textbf{one gate} writes the receipt.}
  \vspace{0.2cm}
  \note{
    \textbf{(45s, ends 1:21)} Here is the risk. An AI agent with tools can read that text
    and act at once. It believes the claim, books the thirty five dollar backup, and
    reshuffles the whole program. That top lane is an illustration, not one of the systems I
    tested. Plan B works differently. First it checks the one fact that matters. Then the
    server builds the possible fixes and checks each one. The language model only picks one
    of them. And every change passes one gate that writes a receipt, the server's own record
    of the change. The model chooses. The server decides what is allowed.
  }
\end{frame}

% 6. THE DESIGN (62 s)
\begin{frame}{The model only picks among options the server built and checked, and one gate writes every receipt}
  \vspace{0.05cm}
  \begin{center}
    \includegraphics[width=0.84\textwidth]{fig_design.pdf}
  \end{center}
  \vfill
  \support{\textbf{The model}: Claude Sonnet 5.5 (\texttt{anthropic/claude-sonnet-5.5}) through the OpenRouter API, the same model and settings for all three model approaches. Only how the model is used differs. Spending starts as a \textbf{hold}, a free reservation that expires on its own, until a person approves.}
  \vspace{0.2cm}
  \note{
    \textbf{(60s, ends 3:44)} Here is how it works. Think of a restaurant. The kitchen decides
    what can be served, the waiter picks from the menu, a manager signs off on anything that
    costs money, and every order gets a ticket. In Plan B the server is the kitchen. Its planner builds
    the options and checks each one. The language model is the waiter. Its only outputs are a checked
    reading of the message and one option from the server's list. It holds no tool that
    writes. Every change, from the model or a person, passes one gate. Is it allowed for
    this role? Is the plan still current? Is it within budget? Spending starts as a hold, a
    free reservation that expires on its own, until a person approves. The gate writes the
    receipt.
  }
\end{frame}

  \support{\textbf{The runs}: each new case ran 10 times, the fixed rules once (no model) and each model approach 3 times, all on Claude Sonnet 5.5 through OpenRouter. 4 campus cases make 40 runs, 2 pantry cases make 20. \textbf{No executed action broke a rule}: the gate refused \res{fresh:both:refused} attempts and recorded each.}
  \vspace{0.05cm}
  \figcaption{\textbf{The six new cases.} Campus: a real projector delay, a believable false alarm, a volunteer who runs late and then checks in, and a disruption with no allowed fix. An earlier \res{dev:cases}-case test found real defects, fixed before the freeze.}
  \note{
    \textbf{(64s, ends 4:48)} Does it work? I froze the code, the prompts, the model and the
    limits. Then I ran six new cases, written by a separate worker before the freeze and
    locked with it. Fixed rules ran once per case, the model approaches three times each, all on the same model, Claude Sonnet 5.5. Fifty nine of sixty runs met the expected
    outcome. Our coordinator met all eighteen of its runs, and so did the other two model
    approaches. The one miss was the fixed rules, in a case where a volunteer runs late,
    because a person's own delay is a message its rules cannot read. No action ever broke a
    rule in these runs, because every change passes the one gate. It refused six attempts and recorded
    each. With six cases there is no ranking. The point is safety and reliability. An
    earlier, larger test is how I found and fixed real defects before this freeze.
  }
\end{frame}

\begin{frame}{Backup: what these numbers do not show}

  \vspace{0.4cm}
  \support{\textbf{The earlier locked test, before the fixes.} Our coordinator met every run of \res{campus:P2:cases} of \res{campus:P2:ncases} campus cases there, and the tool-calling model of \res{campus:P1:cases} of \res{campus:P1:ncases}. Those failures are what the fixes target. A rerun on those spent cases is a diagnostic, not a test and not comparable as an improvement: our coordinator meets every run of \res{rerun:campus:P2:cases} of \res{rerun:campus:P2:ncases} campus cases there and still misses one case in all three runs. The documentation has the full record.}
